# Tickera v1.0.0 — High-Concurrency Ticket Booking System

Tickera is an engineering portfolio project that explores how a ticket booking
system can remain correct, reliable and observable under concurrent load. This
release marks the reference implementation as complete: the behaviours that
were investigated experimentally are implemented, tested and documented.

The project is intentionally not presented as a production-ready commercial
platform. It is a local, reproducible system for studying concurrency control,
idempotency, distributed coordination, reliable messaging and observability.

---

## Highlights

- **High-concurrency ticket booking** with an explicit single-booking
  invariant.
- **Pessimistic and optimistic locking**, implemented and compared under
  different contention patterns.
- **Redis distributed seat holds** with `SET NX`, TTL and ownership checks.
- **Concurrent request idempotency** using a unique idempotency record and
  request fingerprinting.
- **Kafka transactional outbox** so booking state and event intent commit
  atomically.
- **Acknowledgement-based publishing** that does not mark an event as
  published before Kafka confirms the send.
- **Retry, backoff and stale processing recovery** with explicit state
  transitions and a bounded retry policy.
- **At-least-once delivery and an idempotent consumer** so duplicate
  deliveries do not produce duplicate side effects.
- **Prometheus and Grafana observability** with provisioned dashboards and
  alert rules.
- **k6 load testing** with six maintained scripts and prepared test data.
- **Testcontainers integration tests** against PostgreSQL, Redis and Kafka.
- **GitHub Actions CI** running the full Maven verification on Java 21.

## Correctness guarantees

```text
A seat is never booked twice
A client retry does not create a second booking
A committed booking eventually produces an event
A duplicate event does not create a duplicate side effect
A slow Kafka broker does not corrupt booking state
```

These guarantees are enforced by database constraints, row-level locking,
idempotency records, the outbox state machine and the consumer-side
`processed_events` table. They describe the implemented behaviour of this
reference system, not a service-level guarantee.

## Reliability model

```text
POST /bookings
      │
      ▼
PostgreSQL transaction
├── Seat → BOOKED
├── Booking INSERT
├── Idempotency record → COMPLETED
└── Outbox event → PENDING
      │
      ▼
COMMIT
      │
      ▼
OutboxPublisher
      │
      ├── PENDING → PROCESSING (claimed)
      ├── publish to Kafka (ack awaited, 10s timeout)
      │
      ├── ACK   → PUBLISHED
      ├── fail  → PENDING + nextRetryAt (2s / 5s / 10s / 30s)
      └── max 5 → FAILED (manual requeue available)
      │
      ▼
Kafka: booking-created
      │
      ▼
Idempotent consumer → processed_events
```

Delivery is **at-least-once**. A lost acknowledgement can produce a duplicate
record, so duplicate safety is enforced on the consumer side rather than
assumed from the producer.

## Observability

Prometheus collects application, HTTP, database pool, JVM and outbox metrics.
Two Grafana dashboards are provisioned from files:

```text
Tickera — Application Overview   uid: tickera-application-overview
Tickera — Outbox & Kafka Reliability  uid: tickera-outbox-kafka
```

Prometheus alert rules cover target availability, HTTP 5xx ratio, outbox
backlog and failed events. The rules use development thresholds and have no
Alertmanager notification channel.

```text
Actuator health   http://localhost:8080/actuator/health
Prometheus        http://localhost:9090
Grafana           http://localhost:3000
```

## Testing and continuous integration

- `./mvnw clean verify` runs **35 tests** on Java 21, all passing.
- Integration tests use real PostgreSQL, Redis and Kafka containers.
- GitHub Actions runs the same verification on every push and pull request to
  `main`.
- All six k6 scripts are validated with `k6 inspect`.

Controlled smoke runs were used to validate the k6 scripts against the current
API contract:

```text
hot-seat.js          1 × 201 and 4 × 409 with 5 virtual users
concurrent-booking   1 × 201 and 4 × 409 with 5 attempts
parallel-booking     5 × 201 with 5 virtual users
sustained-load       10 × 201 plus one expected wrap conflict
capacity-test        11 × 201 with 12 prepared seats
idempotency-replay   201 → 201 (same booking) → 409 (different seat)
```

These are functional checks, not capacity measurements.

## Performance: historical vs current

`docs/performance-testing.md` contains measurements from the earlier capacity
investigation. They were collected before the current `Idempotency-Key`
requirement and before outbox retry, backoff and stale recovery were
implemented, so they are **not** measurements of this release.

Current numbers must be produced locally with the maintained scripts:

```bash
eval "$(./load-tests/prepare-test-data.sh 100)"
k6 run load-tests/parallel-booking.js
```

See [`load-tests/README.md`](../../load-tests/README.md) for sizing, smoke runs
and full runs. No benchmark results are claimed for v1.0.0.

## Quick start

```bash
docker compose up -d
./mvnw spring-boot:run
```

The application starts on `http://localhost:8080`.

```bash
# Full verification
./mvnw clean verify

# Create a booking
curl -X POST http://localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-key-1' \
  -d '{"seatId": 101, "userId": "demo-user"}'
```

See the [README](../../README.md) for the booking lifecycle, API examples and
setup details.

## Known limitations

- `FAILED` outbox events require manual requeue; there is no dead-letter topic.
- Published outbox rows are not cleaned up automatically; no retention policy.
- Prometheus alert rules have no Alertmanager notification channel.
- Outbox counters are process-local and reset on restart; gauges recover from
  the database.
- Idempotency records are retained indefinitely.
- The Docker Compose stack is a local development topology, not a production
  deployment model.
- Performance figures are local and historical, not capacity claims.
